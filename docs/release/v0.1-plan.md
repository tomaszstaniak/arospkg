# v0.1

## Scope, as decided on 2026-09-19

**Target: ABIv11, AROS One x86_64.** Not ABIv1/mainline. That is where the
software is: 171 ABIv11 candidates in AROS Archives against 7 for mainline, one
of them an x86_64 application. `src/build.sh` builds the ABIv11 binary; the
mainline build moved to `src/build-mainline.sh`, still maintained, and **does
not gate the release**.

**The first release is a command-line client.** A graphical front end and a
storefront are the next stage, with no version number or date attached to them
here or anywhere else.

**Acceptance criterion.** A user of AROS One x86_64 can get the client, install
it by following the README, and search, install, start and remove packages from
the tested twenty.

### In v0.1

- the drawer icon `<root>/<id>.info`: installed, recorded, an existing or
  modified icon protected, removed on uninstall, reconciled by recovery;
- **ZIP and LHA**, chosen by the archive's own first bytes. LHA is the Amiga's
  format and 16 of the 171 ABIv11 candidates use it; the reader is checked
  against the system `lha` over every real archive we hold;
- `requires_system` (library requirements checked on the running machine);
- the three debts from 2026-09-12: `list` sorted, a damaged cache recovered,
  `search` without a fixed buffer: each with a regression test;
- **20 packages, each installed, started and removed on AROS One.** A hash and a
  clean unpack do not qualify a package;
- release tests on AROS One on a persistent volume;
- a release archive, README, licences, checksums, install instructions, the CA
  requirement and the limits.

### Not in v0.1

Package-to-package resolution. General `LIBS:`/`Fonts:` installation. Upgrade.
The GUI. aarch64. Building from source.

**Why `LIBS:`/`Fonts:` moved out.** Of 30 sampled ABIv11 ZIPs, 27 are
applications in a single drawer and none writes to a system directory. That is a
statement about archive **layout**, and layout does not prove a program needs
nothing in `LIBS:` or `Fonts:`, so each candidate's documentation was read as
well, and each is started on the target before approval. Reading found the
first real case at once: ZapHod's manual offers extra fonts for `FONTS:` and a
catalog for `LOCALE:`. Both are optional; ZapHod runs without them, and its
manifest says so.

### Upgrade is not in v0.1, and remove + install is not a substitute

Removal keeps files the user changed. Those files stay in the package's
directory, and `install` refuses a directory of the package's name that has no
registry entry, before downloading, with a message saying why. So after a
removal that kept something, a reinstall is refused until the kept files are
moved away. That path is tested (release suite F3/F4); it is described in the
README as what it is, and not as an update mechanism.

## Test plan

Everything below runs on AROS One x86_64 in QEMU, on the persistent root
`SYS:PkgRel` of the `onetest` disk. Every apkg run is gated with `--expect`; file
contents with `assert-hash`; presence with an explicit PASS/FAIL line. Evidence
is **files**: the console transcript and the joined run reports come back to the
host over the network (`tests/tools/putfile` → `tests/tools/recv.py`), with a
SHA-256 both ends agree on. Screenshots illustrate and prove nothing.

| part | what | script |
|---|---|---|
| B | drawer icon: install, remove, pre-existing kept, modified kept, interrupted at point 8, bad index entry | `release-1` |
| C | list sorted, damaged cache refetched, search on category | `release-1` |
| D | every interruption point 1–8, each followed by recovery, with end-state checks | `release-1` |
| E | commit refused; leftovers report refused | `release-1` |
| F | user data: install refused over a kept directory; moved away and reinstalled; recovery itself interrupted and finished by a re-run | `release-1` |
| G | a registry entry written by the previous binary, removed by this one | `release-1` |
| H | interrupted install, **real reboot**, recovery | `release-1` → reboot → `release-2` |
| I | TLS refusals N1–N4, with a positive control | `release-2` |
| n/a | 20 packages: install, start, remove | `trial-a`, by hand, `trial-c` |

## Result (2026-09-20)

Every suite passed on binary `f2e180cc`, which is the `apkg` in
`dist/arospkg.x86_64-aros-v11.zip`. The evidence, and the three code bugs the
runs found that reading had not, are in
[`../reports/2026-09-19-v01/README.md`](../reports/2026-09-19-v01/README.md).

The acceptance criterion was run as written: from the release archive, a user
unpacks it with `UnZip`, copies `apkg` to `C:`, and then updates, searches,
installs Soliton from AROS Archives, starts it, lists, and removes it. The
index it used is the published one, with 23 packages.

**What is left before publishing** is a set of decisions, not work:

- the licence (the archive proposes MIT; this repository has never carried one);
- whether the source repository becomes public, and the contact address in the
  upload (`release/UPLOAD.txt` lists both);
- the upload to AROS Archives itself.

A `v0.1` tag is prepared locally and not pushed.

**F3 changed meaning.** The old F3 reached the publish window by installing over
an unregistered directory. Install now refuses that directory up front, so the
window with an existing destination no longer opens in normal use, and F3
asserts the refusal and that the user's files are untouched.
