# Package layout and testing

For arospkg 0.7.3 and apkg-pack 0.2.0. To create and submit a new package, follow the [publishing guide](authoring.md). This page covers archive layout, target testing and existing archives maintained by someone other than their author.

## 1. The archive

`apkg-pack build` creates a ZIP from a finished application drawer:

```text
myapp.zip
├── .arospkg/manifest.toml   package description, read by apkg-pack submit
├── MyApp.info              drawer icon
└── MyApp/
    ├── MyApp               executable
    ├── MyApp.info          program icon: stack and tool types
    ├── application.json    generated when [launch] is present
    └── Data/
```

With `id = "myapp"` and `subdir = "MyApp"`, the drawer's contents are installed into `SYS:Packages/myapp/`. The file named by `icon` becomes `SYS:Packages/myapp.info`. Files outside `subdir`, including the embedded manifest, are not installed. With an empty `subdir`, the whole archive is installed, including `.arospkg/` if present.

The program must tolerate its drawer being renamed or moved. Use `PROGDIR:` for resources, and check that save requesters do not depend on a fixed installation path. The drawer icon and the program icon have different jobs; a Workbench launch needs a tool icon beside the executable.

Empty drawers are preserved. File protection bits and comments are not restored, so a script that needs the `s` bit should be started with `Execute`. Put the required stack size in the program icon for a Workbench launch.

Existing ZIP and LHA uploads can also be listed. Supported ZIP methods are stored and deflate; supported LHA methods are `-lh0-`, `-lh5-`, `-lh6-`, `-lh7-` and directory entries, with header levels 0–2.

| Limit in arospkg 0.7.3 | Maximum |
|---|---|
| Downloaded archive | 64 MiB |
| One unpacked ZIP member | 128 MiB |
| One unpacked LHA member | 64 MiB |
| All unpacked members | 256 MiB |
| Drawer icon | 1 MiB |
| Files in a package | 2048 |
| Path inside the installed drawer | 255 bytes |

Use relative paths with `/` separators. Avoid absolute paths, volume names, `..`, control characters and names that differ only in case. Run `apkg-pack check` before publishing; the catalogue review also checks archive paths and layout.

## 2. Identity and versions

Keep a stable lowercase `id`, at most 63 characters. It names the installed drawer and the package record.

Use `version` for the program's version. Increase `revision` for another AROS build or packaging correction of that version; omit it for an initial release if you prefer. The client displays revision 2 as, for example, `1.0-aros2`. Changed archive bytes need a new version or revision.

`upgrade` supports newer versions as well as newer packaging revisions. It orders dotted numbers, optionally followed by `-testN`, `-previewN` or `-rcN`, and a `-rN` rebuild suffix. It refuses downgrades and versions it cannot order. Keep one version scheme for a program; see [upgrades](using.md#keep-things-up-to-date).

## 3. Target and requirements

Set `arch` and `abi` from the build configuration. Supported CPU names are `x86_64`, `i386` and `aarch64`; ABI names are `v0`, `v1` and `v11`. CPU detection does not identify the ABI. A filename without an ABI suffix is not evidence that the binary is v1.

Each (`id`, `arch`, `abi`) is a separate catalogue variant. Publish v1 and v11 builds as separate entries. Matching CPU and ABI allow installation; they do not establish that the application runs.

Use `requires_system` for libraries the system must provide. Use `depends` only for packages your program can find in the same package root. arospkg does not copy libraries to `LIBS:`, install shared commands or create assigns. See the [relations reference](metadata.md#relations).

## 4. The manifest

For your own program, keep the description generated by `apkg-pack init` and let `submit` calculate the download fields. For an existing upload without an embedded manifest, a catalogue maintainer writes `manifests/<id>.<arch>.<abi>.toml`.

The following is a historical Micropolis 0.1.0-rc3 entry, retained as a complete, automatically checked format example. Its download measurements and platform claims describe that old archive, not current Micropolis builds. Replace them with evidence for the archive you are submitting.

<!-- validate: manifest -->
```toml
status          = "approved"
id              = "micropolis"
version         = "0.1.0-rc3"
revision        = 1
summary         = "Classic city-building simulation for AROS"
arch            = "x86_64"
abi             = "v11"
category        = "game/strategy"
license         = "GPL-3.0-or-later with EA Section 7 terms; Micropolis Public Name License"
url             = "https://github.com/tomaszstaniak/aros-micropolis/releases/download/v0.1.0-rc3/micropolis.x86_64-aros-v11.lha"
size            = 2593505
sha256          = "c46bbc14274af53fb4452f59081fbcf28f1ce5fffb534c06d169b0b1911cd124"
kind            = "app"

depends         = []
depends_checked = true
subdir          = "Micropolis"
icon            = "Micropolis.info"
installs_on     = ["aros-one"]
runs_on         = ["aros-one"]
does_not_run_on = ["mainline-x86_64"]

[[requires_system]]
type = "library"
id   = "crt.library"

[[requires_system]]
type = "library"
id   = "m.library"

[[requires_system]]
type = "library"
id   = "stdlib.library"

[source]
repository = "https://github.com/tomaszstaniak/aros-micropolis"
revision   = "v0.1.0-rc3"
archive    = "Micropolis-AROS-0.1.0-rc3-source.zip"
sha256     = "969be5094991e8c57b9689da06e68c4082daf4491a907411db0972aa3635e5e5"
built_with = "abiv11-x86_64, GCC 10.5.0"
```

To validate maintainer entries from an arospkg source checkout, put them in a scratch directory and run:

```text
python3 tools/mkindex.py --manifests draft/manifests --out-dir draft/generated
```

This validates metadata and generates the catalogue files. It does not download or run the application. The catalogue's review workflow checks the published archive before merging the submission. Do not edit generated indexes by hand.

## 5. Testing on AROS

Test the ZIP you intend to publish on each CPU and ABI you claim to support:

1. Unpack it into a temporary drawer. Start the program from its icon and exercise a normal task, including saving and reopening data where applicable.
2. Check launch metadata with `apkg run --check "Work:Test/MyApp"`, then run it with `apkg run "Work:Test/MyApp"`. Also try the drawer under a different name and path.
3. For a maintainer's test catalogue, install into a separate package root. Check `show`, `run`, `verify` and removal. For an update, test upgrading from the previous published archive and rolling back.
4. Add a user file and modify a packaged file. Confirm that removal keeps both and reports them. Check that an upgrade does not overwrite a local change.

`apkg-pack check` validates the archive; it does not replace these runtime tests. Record the system, CPU, ABI, archive SHA-256, date and operations actually tested. Keep untested targets explicit. Maintainers can add the result to [runtime-tests/](metadata.md#runtime-tests).

## 6. Publishing

Authors: [upload and submit with apkg-pack](authoring.md#4-upload-and-submit).

Maintainers: submit the manifest to [arospkg-index](https://github.com/tomaszstaniak/arospkg-index). Keep corrections in `overrides/` and runtime evidence in `runtime-tests/`. The workflow owns `review/`, `history.json` and the generated indexes. See [maintainer notes](authoring.md#notes-for-maintainers).
